# FINANCE_TUNNEL_SCRIPT_REVIEW

日期：2026-10-30。范围：只读 `D:\develop\providerapi\scripts\newapi-tunnel-open.cmd`。没有启动隧道，没有连接服务器，没有改脚本，没有读取私钥。

## 1. 脚本在做什么

这是一个 Windows `cmd` 启动器。它另开一个最小化窗口运行 OpenSSH，把本机端口转到腾讯云主机上的 loopback 服务，再用 `curl` 看本机是否返回 HTTP 200。成功则打开浏览器。失败则打印一条需要手工执行的命令。

脚本没有使用 Plink、`ssh -R`、`ssh -D`、ProxyJump 或 ProxyCommand。

## 2. 转发机制

实际机制是 **SSH Local Forward**（`ssh -L`）。

| 方向 | 参数 | 含义 |
|---|---|---|
| 本地转发 | `-L 3100:127.0.0.1:3100` | 本机收到的连接，经 SSH 送到远端眼里的 `127.0.0.1:3100` |
| 不执行远端命令 | `-N` | 只做转发 |
| 远程转发 | 无 `-R` | 没有把远端端口开回本机 |
| SOCKS | 无 `-D` | 不是动态代理 |
| GatewayPorts | 脚本未设置 | 没有要求对局域网开放本地端口 |

远端目标 `127.0.0.1` 是 SSH 服务器自己的 loopback，不是员工电脑的 loopback。它对应的是该主机上 New API 的本机端口，不是 Finance 的 `4173`。

SSH 服务器是腾讯云 Finance 主机的 22 端口，账号是特权账号 `root`。脚本没有写 `-p`，因此用客户端默认端口 22。

## 3. 监听地址和端口

脚本写成 `-L 3100:127.0.0.1:3100`，没有写绑定地址。

OpenSSH 在 `GatewayPorts` 保持默认 `no` 时，这种写法只绑定本机 loopback。脚本自己没有写 `127.0.0.1:3100:...`，也没有检查用户的 `ssh_config`。如果某台电脑把 `GatewayPorts` 设成 `yes`，本地 3100 可能对局域网可见。这一点脚本没有钉死。

脚本也没有指定只绑 IPv4 或 IPv6。具体是 `127.0.0.1`、`::1` 还是两者，取决于这台 Windows 上的 OpenSSH 版本和配置。本文件没有约束。

## 4. Host Key、私钥和认证

| 项目 | 脚本里的事实 |
|---|---|
| Host Key 校验 | 没有 `StrictHostKeyChecking=no`，也没有 `accept-new`，没有把 `UserKnownHostsFile` 指到空设备。使用客户端默认策略，通常是询问指纹 |
| 自动接受未知主机 | 没有 |
| 私钥 | 没有 `-i`，没有在脚本里写私钥路径或私钥内容。使用 ssh-agent 和该用户默认身份文件 |
| 认证 | 没有硬编码口令。失败提示写了“可能需要输入密码或确认指纹”，说明它依赖交互式确认 |
| IdentitiesOnly | 没有。客户端可能依次尝试多把默认密钥 |

最小化窗口里如果弹出指纹或口令确认，操作者不容易看见。这不是关闭校验，但会让校验停在一个被藏起来的窗口里。

## 5. 秘密和暴露面

脚本正文没有口令、Token、API Key 或私钥。主机地址和 `root` 账号是运维目标，不是可重放的凭据。

没有远程端口转发，所以脚本不会在服务器上新开一个面对公网的转发口。

风险不在“写了秘密”，而在：

- 使用 `root`，权限大于转发一个端口所需。
- 本地绑定地址没有写死，可能被本机 SSH 配置放宽。
- 没有 `ExitOnForwardFailure=yes`。本地 3100 已被占用时，转发可能失败，但 SSH 会话仍可能保持。
- 成功标准只是 `curl` 得到 HTTP 200。本机若已有别的程序占着 3100 并返回 200，脚本会把那次访问当成隧道成功。

## 6. 断线、重连、退出、端口冲突

保活参数：

- `ServerAliveInterval=60`
- `ServerAliveCountMax=3`
- `TCPKeepAlive=yes`

服务端连续不应答大约三次保活后，SSH 退出。脚本没有循环，没有 autossh，也不会再打开隧道。断线后浏览器里的入口失效，必须有人重新运行脚本。

退出方式是关掉标题为 `SSH Tunnel - NewAPI` 的窗口。启动器自己停在 `pause`。关掉启动器不会自动关掉已经 `start` 出去的隧道窗口。

端口冲突没有单独处理：不等待 SSH 进程报告转发成功，只固定等 3 秒再请求 `http://127.0.0.1:3100/`。返回值不是 200 就打印失败，并建议手工执行同一条转发命令。它不结束已经存在的占用进程，也不换端口。

临时文件只写 HTTP 状态码，随后删除。没有 SSH 调试日志路径。

## 7. 和 Finance 4173 的差距

这条脚本不能打开 Finance。它转发的是远端 `3100`。Finance 应用监听的是远端 `127.0.0.1:4173`。

若只把端口数字改成 4173，浏览器会访问 `http://127.0.0.1:4173`。互联网那一跳在 SSH 里面，不是公网明文 HTTP。但浏览器到本机端口这一段仍是 HTTP，应用看到的 Host 是 `127.0.0.1:4173`。当前生产标签把 `FINANCE_COOKIE_SECURE` 设为 0，这种 HTTP 还能收下会话 Cookie。一旦改为 1，浏览器会丢掉 Secure Cookie，登录看起来不会保持。

更完整的适配放在 `FINANCE_TUNNEL_ACCESS_DESIGN.md`。本轮没有创建隧道脚本，也没有改这台主机的 Nginx。
