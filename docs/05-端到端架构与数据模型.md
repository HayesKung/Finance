## 1. 北极星

以一名财务负责人 + 一名支撑人员为基本运营单元，支持面向中国出口企业及海外工程项目客户的专业财务外包服务。目标不是堆叠页面，而是形成可控、可追溯、可重复交付、能够复购的业务闭环：

线索 → 资格筛选 → 预约诊断 → 风险清单 → 付费方案 → 资质/授权审核 → 合同签署 → 预收款核验 → 项目执行 → 资料核验与工作底稿 → 专业复核 → 交付 → 收尾对账 → 月度复盘 → 续约/转介绍。

每一环必须有责任人、状态、进入条件、证据、截止日期、异常处理及下一步动作。目标值、草稿、口头反馈、未核验数据不能记为实际完成。

## 2. 业务范围与不可变原则

### 2.1 首期产品

1. 出口财务包：单据核对、收汇核对、退税资料整理、汇率风险提示。
2. 海外项目财务托管：项目预算、资金计划、进度结算跟踪、月度财务包、回款预警。
3. 结算与清欠专项：合同、签证、结算单、发票和付款记录对齐，输出可追溯的财务核对口径。

Drive 方案中的价格为起步建议价，不是市场核实价或收入承诺。系统不得自动向客户报价；财务负责人须结合工作量、服务范围、能力与资质确认价格。

### 2.2 红线

- 不经手客户项目资金，不垫资、不入股、不做资金过桥。
- 不承诺退税金额、贷款额度、回款结果或投资收益。
- 代理记账、税务申报、审计、法律意见等活动须先核实适用的资质与执业要求；不满足时转交符合要求的专业机构。
- 不买名单、不爬取私人联系方式、不群发骚扰；私人联系方式仅在对方同意后记录。
- 客户资料按客户和项目隔离。案例公开必须有书面授权、脱敏、风险边界说明和负责人确认。
- AI 和支撑人员可以整理、检查、起草、提醒，但不得冒用财务负责人或委托人的身份对外联系、报价、签约或发布。
- 未经授权，不开放公网、不发布官网、不购买域名或付费服务、不执行生产变更。

## 3. 现状与目标必须分开

截至本次文档编制，仓库文档确认的现状包括：

- 已有前台草案、内部工作台页面，以及线索、诊断、名单、Pipeline、模板、订单和服务确认书相关模块。
- src/lib/finpivot/flow.ts 已定义基础订单状态、收费方式、收款计划、开工和交付门禁。
- src/lib/finpivot/contract-api.ts 通过 src/lib/db.ts 使用 PostgreSQL 持久化服务确认书相关数据，并有通道配置读写逻辑。
- 作战台主数据仍主要保存在浏览器本地；不能把合同 PostgreSQL 误称为统一客户/项目数据库。
- docs/03-本地构建.md 已明确 AuthProvider 当前为透传，不是身份认证或访问控制。
- 文档明确品牌名、域名、联系方式与对外发布仍需本人确认。运行已部署程序不等于已获准对外承接真实客户资料。

以下为目标设计，不得仅凭本文档宣称已经实现：真实服务端认证、角色权限、跨客户数据隔离、统一服务端客户/项目数据模型、受控文件存储、完整审计、正式的电子签名证据链、自动化备份恢复及完整生产 Gate。每一项须以代码、测试、实际环境和可复查证据验证。

## 4. 逻辑架构

### 4.1 触点层

- 对外介绍与需求入口：仅展示已批准的服务内容和起步建议价，收集最少必要信息。
- 客户确认入口：只访问明确授权的服务确认书或交付资源。
- 内部工作台：仅供通过认证并获得相应角色的人员使用。
- 不允许用隐藏导航、noindex 或随机 URL 代替服务端鉴权。

### 4.2 业务域

1. 客户与获客：线索来源、公开联系渠道、同意记录、资格筛选、预约和漏斗。
2. 商务与合同：服务范围、报价确认、合同版本、授权、签署、有效期和变更。
3. 订单与收款：收费方式、应收计划、实收凭证、核销、逾期、退款和冲正。
4. 项目与任务：项目主档、服务周期、负责人、任务、截止日期、阻塞原因和工时。
5. 资料与工作底稿：资料索引、版本、来源、完整性、核对结果、差异及证据引用。
6. 复核与交付：编制、复核、签发、交付包版本、客户确认、纠错与复盘。
7. 经营分析：获客漏斗、签约额、实收、应收、履约、工时、成本、毛利、续约和转介绍。
8. 控制与运行：认证、授权、审计、密钥、保密、备份、恢复、告警和发布。

### 4.3 规则与持久化层

- 业务状态转换在服务端统一执行；前端只负责呈现和收集输入。
- 关键写操作使用事务、版本控制及幂等机制，避免重复签署、重复收款和并发覆盖。
- PostgreSQL 用于结构化业务数据；受控文件存储用于原始凭证和交付文件。文件权限、保留、下载和删除均需审计。
- 不把大批原始凭证或全部业务状态塞入单一 JSON 合同字段。
- 关键状态变更写入追加式审计事件，记录操作者、时间、对象、动作、结果和关联请求 ID；不得记录密钥或不必要的敏感正文。

## 5. 核心数据对象

建议按明确关系设计，而不是用一个浏览器 Store 或一个合同 payload 承载全部业务：

| 对象 | 关键内容 | 控制要求 |
|---|---|---|
| Lead / Inquiry | 来源、公开字段、同意状态、需求、跟进人 | 来源可追溯；未同意不保存私人联系方式 |
| Client | 主体信息、行业、服务资格、授权联系人 | 客户身份与权限范围明确 |
| Engagement / Contract | 服务范围、期限、价格、条款版本、签署证据 | 已签版本不可静默覆盖；变更需留版本 |
| Order | 产品、计费方式、金额、状态、合同引用 | 服务端状态机；禁止越权跳转 |
| Receivable / Receipt | 应收、到账凭证、核销、差异、退款/冲正 | 应收与实收分离；幂等与审计 |
| Project | 客户、合同/订单、服务周期、币种、负责人 | 与客户和订单关联；状态有门禁 |
| Task | 负责人、截止日期、状态、依赖、工时 | 过期和阻塞可追踪 |
| Document / Evidence | 文件索引、来源、版本、哈希、权限、保留期限 | 客户隔离；受控访问；不在公开导出中泄漏 |
| Workpaper | 核对项目、公式/口径、原始证据引用、差异 | 可重算、可追溯；专业判断有责任人 |
| Review | 复核人、范围、意见、问题和签发状态 | 机械完整性检查与专业复核明确区分 |
| Deliverable | 交付物清单、版本、生成时间、接收确认 | 交付版本冻结；更正留痕 |
| Consent / AuditEvent | 授权、案例许可、操作审计 | 可查验、最小化、追加式记录 |

数据建模应遵循最小必要原则。敏感个人信息、银行账户、税务资料等必须先明确业务必要性、合法处理依据、权限、保留和删除机制，不得默认全部采集。

## 6. 三条专业交付工作流

### 6.1 出口财务包

1. 确认服务授权、合同范围和本期业务编号。
2. 收集合同、发票、报关、物流、收汇等约定资料并登记缺失项。
3. 核对主体、金额、币种、日期及单证一致性。
4. 形成差异台账，标明已确认、待客户确认、证据不足和需要专业升级的项目。
5. 整理退税所需资料；涉及正式申报或法定专业判断时，交由符合要求的人员或机构。
6. 由责任人复核后，交付单据核对清单、收汇核对表、资料包、风险提示及待办清单。
7. 记录客户接收、后续事项和归档状态。

### 6.2 海外项目财务托管

1. 建立项目合同额、币种、付款条件、里程碑、质保金及责任人台账。
2. 建立预算、实际成本、已承诺成本及预计完工成本对照。
3. 滚动更新资金计划、进度款、应收账龄和回款预警。
4. 跟踪签证、变更、索赔、结算与付款证据。
5. 每月形成预算差异、现金流、逾期应收、风险与待决事项报告。
6. 复核关键金额、口径、异常解释和数据来源。
7. 交付月度财务包并记录客户确认和下期计划。

### 6.3 结算与清欠专项

1. 确认授权、争议范围、合同与资料保管责任。
2. 关联合同、补充协议、签证、变更、结算单、发票及付款凭证。
3. 逐笔对账并分类已确认、存在差异、证据不足及待确认事项。
4. 形成可追溯的金额核对口径和证据索引。
5. 涉及法律意见、审计或争议性专业结论时升级给相应专业人士。
6. 冻结交付版本，记录客户确认、后续事项及纠错流程。

## 7. 状态机与业务门禁

客户、订单和项目状态是不同维度，不可混为一个状态字段。

- 线索：新建 → 资格筛选 → 已约诊断/未约到/不跟进 → 风险清单 → 付费方案 → 签约或失单。
- 订单：草稿 → 待收款 → 执行中 → 待尾款/待验收 → 已交付；取消、退款和冲正走明确的例外流程。
- 项目：立项 → 进行 → 暂停 → 结项；暂停后恢复必须记录原因和新计划。
- 任务：待办 → 进行中 → 待复核 → 完成；阻塞、驳回和逾期必须可见。
- 资料：待收集 → 已收到 → 待核验 → 已核验/有差异/被拒绝；新版本不得覆盖旧证据。

门禁：
- 未完成必要的合同、授权和资质检查，不得开工。
- 按单业务定金、月度当月预收或阶段首款，按已确认的合同规则核实到账后才可开工。
- 客户自报已转账、支付截图或选择支付方式都不等于到账。
- 交付完成需满足交付清单、必要复核、客户交付流程和合同约定的付款条件。
- 已签合同、已核销收款和已发布交付版本不能静默删除或覆盖；更正必须留痕。

## 8. 安全、隐私和运行要求

- 生产环境必须具备真实服务端身份认证、角色授权和资源级权限检查。
- 所有敏感 API 均需验证身份、角色、客户/资源归属及操作权限。
- 合同分享 Token 必须有足够随机性、到期/撤销、限流和审计；签署应具备并发保护。
- 数据库凭据和第三方密钥只通过受控环境配置或密钥管理系统注入，不提交到 Git。
- 文件存储应使用私有访问、短期授权下载或受控代理；记录下载和共享事件。
- 日志采用脱敏、最小化原则，不写入密码、Token、银行账户或原始财务凭证内容。
- 建立备份、恢复演练、数据保留/删除、事故响应、监控与回滚手册。
- 本地回环监听是必要的部署约束，但不能替代身份认证和授权。
- 对外发布需分别核验品牌、域名、联系方式、内容授权、访问控制及索引范围。

## 9. 两人团队的职责边界

| 工作 | 财务负责人 | 支撑人员 |
|---|---|---|
| 获客 | 关键客户沟通、诊断、报价与签约 | 公开名单、预约、提醒和跟进记录 |
| 收款 | 核实到账、核销及异常决定 | 收款计划、回单整理、逾期提醒 |
| 交付 | 专业判断、关键复核与最终签发 | 资料清单、勾稽检查、底稿整理和任务跟踪 |
| 合规 | 业务范围、资质边界及最终责任 | 保密、归档、权限流程和异常升级 |
| 经营 | 接单、定价、产能及资源决策 | 周报、漏斗、工时和续约提醒 |

一名财务人员与一名支撑人员不等于所有事项均已实现独立双人专业复核。高风险或超出能力范围的工作须引入符合要求的外部专业人士，或拒绝承接。

## 10. 经营指标

经营看板至少包含：
- 新增线索、有效线索、诊断预约及实际完成数。
- 诊断转付费方案率、报价转签约率、签约转首款率。
- 签约金额、真实到账、应收余额、逾期金额和未核销款。
- 进行中项目、缺失资料、待复核、逾期任务和交付周期。
- 客户实际工时、直接成本、项目毛利及产能利用情况。
- 续约、复购、客户投诉、转介绍和案例授权状态。

签约额、实收、收入确认和未履约义务应分别记录。收入确认口径需依据实际合同和适用会计准则，不能把现金流入直接等同于确认收入。

## 11. 实施顺序

1. WP0：生产基线与安全风险核验。
2. WP1：身份、权限、数据隔离和密钥安全。
3. WP2：统一状态机、服务端规则和持久化。
4. WP3：合同、收款、核销、退款及异常对账。
5. WP4：三类服务的资料、底稿、复核和交付。
6. WP5：资质、授权、保密与专业升级。
7. WP6：获客漏斗、经营指标与续约。
8. WP7：部署、监控、备份恢复和回滚。
9. FINAL GATE：以脱敏测试客户执行完整端到端验收。

具体任务、交付物和通过条件见 docs/06-终极任务收敛卡.md 与 docs/07-生产验收与Gate.md。

## 12. 非目标

首期不建设复杂多租户 SaaS，不接管客户银行账户，不默认接入支付网关，不以 AI 代替法定专业判断，不因系统运行成功就推定业务已具备全部执业资质，也不在没有授权时开放公网或发布官网。
